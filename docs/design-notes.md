# 설계 메모 — 코드·문서가 참조하는 설계 문서 요약

이 저장소는 비공개 정본 저장소에서 코드와 실측 문서만 내보낸 것이다. 코드 주석과 README에 남은 「기획서 §n」「ADR-000n」「리서치 tax-office-document-labels §4.2」는 그 정본의 설계 문서를 가리킨다. 여기서는 참조된 부분만 요약한다 — 코드가 왜 그렇게 생겼는지 알 수 있을 만큼만.

## 기획서 §2.1 — 첫 일: 서류 라벨링

- 파일마다 네 라벨을 붙인다: **거래처 · 분류 · 서류 종류 · 기간.** 못 정하면 「보류」가 정식 출력이다.
- 어휘는 실무자가 실제로 쓰는 약칭으로 고정한다(국세청 서식 번호·홈택스 코드는 실무자가 파일명에 쓰지 않는다).
  - 분류 3: 기본서류(상비철) · 정기증빙(매월) · 신고증빙(분기·연간)
  - 서류 종류 15: 사업자등록증 · 임대차계약서 · 법인등기부등본 · 통장내역 · 급여대장 · 근로계약서 · 전자세금계산서 · 종이세금계산서 · 종이영수증 · 4대보험취득확인서 · 거래명세서 · 카드매출매입내역 · 잔액증명서 · 원천세신고서 · 부가세신고서
  - 기간: `2026-08` · `2026-Q2` · `2026-1H` · `2025` · `PERMANENT`(사업자등록증·임대차계약서처럼 기간이 없는 상비 서류)
- 사람이 승인하면 실무 표준 폴더 트리 `[거래처]/00_기본서류` 또는 `[거래처]/[귀속연도]/01_원천세_급여 · 02_통장_증빙 · 03_부가세 · 04_결산_조정`로 옮긴다. 틀려도 파일은 사라지지 않는다.
- 파일명 순서: 기획서 본문에는 `[귀속시기]_[거래처]_[서류명]`이라 적혀 있으나 조사 원천(아래 §4.2 템플릿)은 `[거래처]_[귀속시기]_[서류명]`이다. 코드는 원천을 따른다(`engine/labels.py`).
- 스캔 PDF·팩스·카톡 사진은 로컬 OCR(Tesseract)로 글자를 뽑아 같은 경로로 보낸다. 카톡 축소 사진은 사업자번호·금액의 한 자리(8↔0, 3↔8, 1↔7)가 틀리기 쉬우므로 **숫자가 흔들리면 「보류」**로 보낸다. 그 판정 기준을 잰 기록이 `bench/ocr-calibration.md`다.

## 기획서 §3 — AI 활용 방식: 문서 이해에만 언어모델, 나머지는 규칙

| 단계 | 누가 | 어떻게 |
|---|---|---|
| 파일 열기·글자 추출 | 코드 | PDF·xlsx·hwp·docx 파서, 스캔은 Tesseract |
| 문서 이해 | 소형 언어모델 | 본문을 읽고 `{거래처, 분류, 서류종류, 기간}` JSON만 낸다. 출력 형식은 GBNF 문법으로 강제해 JSON 밖으로 못 나간다 |
| 판정 | 규칙엔진 | 거래처는 등록 목록과 대조(별칭·오타는 근사 매칭), 기간은 정규식으로 재확인, 상비 서류는 `PERMANENT` 고정, 확신이 낮거나 숫자가 흔들리면 보류 |
| 확인 | 사람 | 확인 큐에서 승인·수정. 수정은 기록돼 규칙(거래처 별칭)으로 되돌아간다 |
| 정리 | 규칙엔진 | 표준 폴더·파일명 규칙 적용. 이동 전 원본 보존 |

네 겹을 쌓는다 — ① 문법 강제 ② 어휘 고정(열거형) ③ 규칙 대조 ④ 보류와 확인 큐. 소형 모델에 프롬프트만 던지면 분류 정확도가 무너지므로(1B·3B 제로샷 0.13～0.47) 프롬프트 하나에 기대지 않는다. 같은 파일을 넣으면 같은 라벨이 나오고, 왜 그 라벨인지 인용문이 남는다.

### §3.1 무상태 세션

파일 1건 = 세션 1회. 문서 하나를 읽고 JSON을 내면 컨텍스트를 버린다(`cache_prompt=False`). 대화형 챗봇처럼 KV 캐시가 자라지 않아 메모리와 지연 시간에 상한이 생긴다. 발열은 설정으로 잡는다: 스레드는 코어 수보다 적게(N100 4코어 중 3, 폰은 빅코어만 고정), 문서 사이 3～5초 휴지, 프롬프트 배치 128(`-ub 128`), 컨텍스트 2048 고정, CPU에서는 KV 캐시 양자화를 하지 않는다.

## 기획서 §4.1 — 설치기 자동 최적화

| 재는 것 | 고르는 것 |
|---|---|
| CPU 명령어(x86 AVX1/AVX2, ARM dotprod) | 추론 엔진 빌드 — 공식 llama.cpp 바이너리는 AVX2를 전제해 2013년 이전 CPU에서 SIGILL로 죽는다 |
| RAM 총량·채널 | 모델 크기·컨텍스트. 싱글채널이면 생성 40～45% 손실을 경고 |
| 코어 구성(big.LITTLE) | 스레드 수·코어 고정 |
| 메모리 대역폭 | 2B/3B 선택 |

고정 규칙이 아니라 짧게 재서 고른다. 같은 폰에서 스레드 설정 하나로 서류 한 건이 81초와 426초로 갈린 실측이 `bench/스레드-설정-실측.md`에 있다.

## 기획서 §5.1 — 한 도메인, 네 경로

`/` 랜딩(정적 HTML, 자동 평가기가 읽을 텍스트) · `/try` 체험(준비된 샘플 서류를 고르면 체험 인스턴스가 라벨링해 결과와 확인 큐를 보여준다. 방문자 업로드는 받지 않는다) · `/download` 설치기 · `/phone` 폐폰 설치 절차·실측. 랜딩은 인스턴스와 다른 곳에서 도는 정적 파일이라 인스턴스가 죽어도 링크는 산다.

## 기획서 §5.3 — 성공 기준: 잰 값을 그대로 쓴다

정확도는 텍스트 서류와 OCR 경유 서류를 나눠 축별로 낸다. 성공 기준의 축은 거래처 · 서류 종류 · 기간 세 축이고 분류는 참고다. 확정으로 내보낸 것 중 틀린 비율(자신 있는 오탐)을 따로 센다. **측정값이 목표에 못 미쳐도 숫자를 고치지 않는다** — 「현재 n%, 개선 중」으로 쓴다. 측정은 가명 샘플 세트(`samples/`)로 한다.

## ADR-0007 — 문서 이해는 sLLM이, 정리 규칙은 결정론 엔진이 맡는다

sLLM은 입력 파일을 읽어 거래처·기간·서류 종류 같은 메타데이터만 뽑고, 폴더 구조·파일명 규칙은 대표가 설정한 규칙을 결정론 엔진이 적용한다. 이동 전에는 확인 큐를 거친다. 이유는 셋이다. 1～2B 모델로도 충분해 CPU 전용 원칙이 지켜지고, 「왜 LLM이 필요한가」에 「문서 이해」라는 답이 서며, 모델이 틀려도 파일이 사라지지 않는다. 따름정리: 같은 파일을 넣으면 같은 라벨이 나온다(`tests/test_rules.py`). 「LLM에 다 시키자」는 제안이 오면 이 절을 먼저 읽는다.

## 리서치 tax-office-document-labels §4.2 — 라벨 스키마

2026-09-10 세무·회계 사무소 서류 실무 조사에서 제안된 출력 스키마다. 코드의 `{"client","category","doc_type","period"}`는 이것의 축약이다.

- `client`: 정규화된 거래처 상호 · `category`: `기본서류|정기증빙|신고증빙` · `doc_type`: 위 15종 열거형 · `period`: `{cycle: MONTHLY|QUARTERLY|HALF|YEARLY|PERMANENT, normalized: "2026-08"|"2026-Q2"|"2026-1H"|"2026"|"PERMANENT"}`
- 저장 경로 템플릿: 기본서류 또는 `PERMANENT`면 `{client}/00_기본서류/{client}_{doc_type}.{ext}`, 아니면 `{client}/{year}/{하위폴더}/{client}_{period}_{doc_type}.{ext}`. 하위폴더는 서류 종류별 고정 매핑이다 — 급여대장·근로계약서·4대보험취득확인서·원천세신고서 → `01_원천세_급여`, 통장내역·세금계산서·영수증 → `02_통장_증빙`, 거래명세서·카드매출매입내역·부가세신고서 → `03_부가세`, 잔액증명서 → `04_결산_조정`.
